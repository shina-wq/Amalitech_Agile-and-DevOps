# TaskFlow API

A lightweight REST API for creating, organising and tracking tasks, built over two sprints to demonstrate Agile and DevOps practices.

## Overview

| Item | Choice |
|------|--------|
| Runtime | Node.js |
| Framework | Express |
| Testing | Jest + Supertest |
| CI | GitHub Actions |
| Storage | In-memory (no database) |

### Task model

| Field | Type | Notes |
|-------|------|-------|
| `id` | string | Generated by the server |
| `title` | string | Required, non-empty |
| `description` | string | Optional |
| `status` | string | `todo` \| `in-progress` \| `done` (default `todo`) |
| `createdAt` | string | ISO 8601 timestamp |

### Endpoints

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/tasks` | Create a task |
| `GET` | `/tasks` | List tasks (optional `?status=` filter) |
| `PATCH` | `/tasks/:id/status` | Update a task's status |
| `DELETE` | `/tasks/:id` | Delete a task |
| `GET` | `/health` | Service health check |

### Getting started

```bash
npm install
npm start      # runs on http://localhost:3000
npm test       # runs the test suite
```

## Sprint 0 – Planning

### Product vision

> For individuals who need a simple way to track their work, **TaskFlow** is a lightweight REST API for creating, organising and tracking tasks, delivered reliably through automated testing and continuous integration.

### Product backlog

Estimates use story points on a Fibonacci scale (1, 2, 3, 5, 8) relative to the smallest item (US6). Priority uses MoSCoW.

| ID | User story | Priority | Points | Sprint |
|----|------------|----------|--------|--------|
| US1 | As a user, I want to **create a task** so that I can record work I need to do. | Must | 3 | 1 |
| US2 | As a user, I want to **list all tasks** so that I can see my workload. | Must | 2 | 1 |
| US3 | As a user, I want to **update a task's status** so that I can track progress. | Must | 3 | 1 |

**Total:** 17 points

### Acceptance criteria

**US1 – Create a task**
- Given a valid `title`, when I `POST /tasks`, then I receive `201` with the task including `id`, `title`, `status: "todo"` and `createdAt`.
- Given an optional `description`, it is saved and returned with the task.
- Given a missing or empty `title`, then I receive `400` with an error message.

**US2 – List all tasks**
- When I `GET /tasks`, then I receive `200` with an array of all tasks.
- Given no tasks exist, then I receive `200` with an empty array.

**US3 – Update a task's status**
- Given an existing task and a valid status (`todo`, `in-progress`, `done`), when I `PATCH /tasks/:id/status`, then I receive `200` with the updated task.
- Given an invalid status, then I receive `400` with an error message.
- Given a task ID that does not exist, then I receive `404`.

**US4 – Delete a task**
- Given an existing task, when I `DELETE /tasks/:id`, then I receive `204` and the task no longer appears in `GET /tasks`.
- Given a task ID that does not exist, then I receive `404`.

**US5 – Filter tasks by status**
- When I `GET /tasks?status=done`, then I receive `200` with only tasks of that status.
- Given an invalid status value, then I receive `400` with an error message.

**US6 – Health endpoint**
- When I `GET /health`, then I receive `200` with `{ "status": "ok" }` and the service uptime.

**US7 – Logging and error handling**
- Every request is logged with method, path, status code and response time.
- Unexpected errors return `500` with a generic message and are logged with details.
- Requests to unknown routes return `404` with an error message.

## Sprint 1 – Retrospective

### What went well

- All planned stories were delivered and meet their acceptance criteria.
- Tests were written alongside each story, so every feature was verified before moving on.
- Setting up CI early meant every later commit was tested automatically.
- Work was committed in small steps, one per task.

### What didn't go well

- **Tooling issue:** Jest 30 failed on Windows because its native resolver needs the Visual C++ Redistributable. Downgrading to Jest 29 fixed it but cost time, and `npm audit` now reports a known issue in Jest 29's dev-only dependencies.
- **Inconsistent commit messages:** only some commits used the `type(story): message` format, which makes the history harder to trace back to stories.
- **Acceptance criteria drift:** extra rules were added during US1 (trimming titles, rejecting a description that isn't a string) without updating the acceptance criteria first.
- **Evidence collected late:** screenshots and test output were gathered at the end of the sprint instead of as each story was finished.

### Improvements for Sprint 2

| # | Improvement | How it will be applied |
|---|-------------|------------------------|
| 1 | Consistent, traceable commits | Use [Conventional Commits](https://www.conventionalcommits.org/) with the story ID, e.g. `feat(US4): …` |
| 2 | Refine before building | Update a story's acceptance criteria in the README *before* implementing any new rule |
| 3 | Capture evidence as we go | Save test output and CI screenshots to `docs/screenshots/` when each story is done |
| 4 | Check tooling up front | Check a new dependency's platform requirements before adopting it |
